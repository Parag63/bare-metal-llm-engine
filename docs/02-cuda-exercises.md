# 02 — The CUDA exercise ladder

Nine kernels, in order. Each one introduces exactly one new idea and reuses everything
before it. Exercise 1 is written for you as a worked example; you write 2 through 9.

| # | Kernel | New idea | File |
|---|---|---|---|
| 1 | `vector_add` | threads, blocks, grid-stride loops | `kernels/vector_add.cu` (**worked**) |
| 2 | `reduce_sum` | threads cooperating: shared memory, `__syncthreads`, warp shuffles | `kernels/reduce_sum.cu` |
| 3 | `softmax_rows` | per-row reduction, numerical stability, two reductions in one kernel | `kernels/softmax.cu` |
| 4 | `rmsnorm` | reusing a reduction you already wrote | `kernels/rmsnorm.cu` |
| 5 | `matmul_naive` | 2-D indexing, and a kernel whose problem is memory traffic | `kernels/matmul_naive.cu` |
| 6 | `matmul_tiled` | shared-memory tiling, data reuse, the payoff | `kernels/matmul_tiled.cu` |
| 7 | `gemv` | column-tiled decode matrix-vector, cooperative warp reduction over $K$, float2 loads | `kernels/gemv.cu` |
| 8 | `rmsnorm_linear` | fusing normalization with projection in shared memory, eliminating DRAM roundtrip | `kernels/rmsnorm_linear.cu` |
| 9 | `residual_rmsnorm` | single-pass residual addition + RMSNorm, saving memory traffic | `kernels/residual_rmsnorm.cu` |

Every one of them has a CPU twin in `include/engine/cpu_ref.hpp` with an identical
signature, a set of golden files generated by `tools/gen_reference.py`, a test in
`tests/test_kernels.cu`, and a row in `bench/bench_kernels.cu`. The scaffolding is
already there; the `__global__` functions are what is missing.

## The rules

**Read the stub's header comment before writing anything.** Each one contains the
spec, the algorithm sketch, the specific pitfalls for that kernel, and an acceptance
criterion. They are long on purpose. The comment in `reduce_sum.cu` alone will save you
more time than it takes to read.

**Correctness first, always.** `ctest -R kernels` before `bench_kernels`, every time.
Optimising a wrong kernel means carefully tuning the wrong arithmetic, and you will not
notice, because a fast wrong answer looks exactly like a fast right answer in a
benchmark table.

**Make it work, then make it fast, and keep both.** When you optimise a kernel, do not
delete the version that worked. `matmul_naive` and `matmul_tiled` are separate files for
precisely this reason: exercise 6's result is meaningless without exercise 5 to compare
it against, and `kernels.matmul_tiled_agrees_with_matmul_naive` uses the simple one as
an oracle for the clever one.

**Predict before you measure.** Write down what you expect the speedup to be and why,
then run the benchmark. When the prediction is wrong you have learned something
specific; when you did not make a prediction, a number is just a number. This is also
the single most useful habit for the mentor checkpoints — "I expected 8x from a 16-wide
tile and got 3.4x, because..." is a much stronger position than a table.

**One exercise per commit.** With the test result and the benchmark delta in the message.

## How you know you are done

Three independent signals, and you want all three:

```bash
build/bin/engine_tests --filter=kernels.        # correctness vs float64 reference data
build/bin/bench_kernels                        # speed, and % of peak bandwidth
build/bin/bench_cpu_ref                         # the denominator for any speedup claim
```

The test suite marks unwritten kernels as `[pending]` — they do not fail the run, they
just do not pass yet. When you implement one, the harness notices:

```
[PENDING-PASS] kernels.reduce_sum_matches_reference  <-- implemented! change TEST_PENDING to TEST
```

Do change it. A `TEST_PENDING` that passes is not protecting you from anything: a
regression would silently return it to "pending" and nothing would go red.

## Why the tests compare against float64 and not against your CPU code

Three tiers:

1. `tools/gen_reference.py` computes the answer in float64 with PyTorch or NumPy and
   writes it to `tests/golden/`.
2. `src/cpu_ref/*.cpp` is a scalar C++ implementation, checked against tier 1.
3. Your CUDA kernel, also checked against **tier 1** — not against tier 2.

That last point is the one that matters. If the kernel were checked against your own CPU
code, a misunderstanding shared by both would pass every test. Comparing both
independently to an external float64 answer means a shared misconception has to survive
two separate implementations and an independent numerical reference, which it generally
does not.

This is also why the tolerances in `tests/test_kernels.cu` are *derived* rather than
tuned until green. Each one carries its arithmetic in a comment. That matters in both
directions: a tolerance that is too tight makes you hunt a bug that is float rounding,
and one that is too loose lets a real bug through. When a test fails, the harness prints
a hint if the worst relative error is within 10× of `rtol`, because that is almost
always rounding rather than a logic error.

A few of the derivations are worth knowing before you start, because they tell you what
"correct" even means for each kernel:

- **`vector_add` must be bit-exact.** One rounding on each side, no accumulation, so
  `rtol = atol = 0`. If it does not match exactly, it is wrong — there is no rounding
  argument available to you.
- **`reduce_sum` is held to a *tree* accuracy bound**, `log2(n) · u · Σ|x|`, not the
  sequential `(n−1) · u · Σ|x|`. At n = 2²⁰ those differ by a factor of ~52,000. A GPU
  tree reduction is structurally *more accurate* than the obvious CPU loop, and the
  test asserts that: a kernel that quietly degenerates into one thread accumulating
  serially fails, even though its answer looks about right.
- **`softmax` error is dominated by rounding the shifted argument**, `u · |x − max|`.
  The edge-case file shifts by about 40, giving 2.4e-6, hence `rtol = 1e-5`.
- **`matmul`'s bound applies to `Σ|aₖbₖ|`, not to `|C|`.** With random inputs those
  differ by about √K because of cancellation, which is why that test carries an
  absolute tolerance of 5e-5 rather than relying on `rtol` alone.

You do not need to re-derive these. You do need to be able to explain, at a checkpoint,
why `vector_add` is bit-exact and `reduce_sum` is not.

## Read the roofline before optimising

Arithmetic intensity — FLOPs per byte of unavoidable DRAM traffic — tells you which
resource limits a kernel *before* you write it. On the RTX 4090 the balance point is
around **82 FLOP/byte** (~82.6 TFLOP/s FP32 against ~1008 GB/s of bandwidth).

| Kernel | AI (FLOP/byte) | Limited by | So the goal is |
|---|---|---|---|
| `vector_add` | 0.08 | memory, by ~1000x | reach peak bandwidth; the add is free |
| `reduce_sum` | 0.25 | memory | reach peak bandwidth without serialising on syncs |
| `rmsnorm` | 0.5 | memory | one pass over the data, coalesced |
| `softmax_rows` | 0.6 | memory | fuse the passes |
| `matmul` 1024³ | 170 | **compute** | arithmetic efficiency and data reuse |

Read the middle column before touching a kernel. Exercises 1–4 are memory-bound: there
is nothing to gain from clever arithmetic, and the only questions are how much traffic
you generate and whether it coalesces. Exercise 6 is the first kernel in the project
where being clever about arithmetic can win anything at all — which is exactly why the
ladder ends there.

`bench_kernels` prints the AI column so you can check your reasoning against the
measurement.

## Exercise 1 — `vector_add` (worked example)

`out[i] = a[i] + b[i]`.

**Do not skip this.** Read `kernels/vector_add.cu` end to end before starting exercise
2. It is the only file in the project where every line is explained, and it establishes
the conventions that the other five follow: the launcher/kernel split, the grid-stride
loop, `__restrict__`, the early return on empty work, `CUDA_CHECK_KERNEL()` placement,
and how the block size is chosen.

The test for it (`kernels.vector_add_is_bit_exact`) is already green on Machine B, so
it also serves as a check on your *environment*: if that fails on a fresh clone, the
problem is the build or the driver, not your code.

Three things from it that generalise:

- **A grid of zero blocks is `cudaErrorInvalidConfiguration`.** Hence the early return
  on `n == 0` in every launcher. `kernels.empty_work_is_a_no_op_not_an_error` locks this
  in for all six kernels.
- **A launch returns before the kernel runs.** Errors surface at the *next* CUDA call,
  which is why every API call is wrapped in `CUDA_CHECK` and every launch is followed by
  `CUDA_CHECK_KERNEL()`.
- **A grid-stride loop decouples the grid size from `n`.** The kernel is correct for any
  `n` with any grid, which means you can tune occupancy without touching correctness.

## Exercise 2 — `reduce_sum`

`out[0] = Σ x[i]`.

**This is the most important exercise on the ladder.** In exercise 1, thread *i* touched
element *i* and finished; no thread needed to know anything about any other. A reduction
is the opposite: every thread holds a partial result that has to be combined into one
number, so the threads must communicate. That is a different kind of problem, and the
pattern you build here is reused directly by exercises 3 and 4, and again by the
row-max/row-sum machinery inside FlashAttention in early 2027. Time spent here is repaid
three times.

The core difficulty: **threads in different blocks cannot synchronise.** A single kernel
cannot cleanly collapse the whole array to one value in one step. `reduce_sum.cu` lays
out the two standard ways around that, the three within-block techniques from slowest to
fastest, and the pitfall that produces results which are *usually* right — which is the
worst possible failure mode. Read it there; it is more specific than a summary would be.

One thing worth pulling out, because it is a good report paragraph: implement the
deterministic two-stage version first, then the `atomicAdd` variant, and compare them on
both speed *and* run-to-run reproducibility. Floating-point addition is not associative,
so the atomic version's answer depends on the order blocks happen to finish. It is
faster and it is non-deterministic, and being able to discuss that trade-off concretely
is worth more than either kernel alone.

## Exercise 3 — `softmax_rows`

Row-wise softmax of a `rows × cols` row-major matrix.

Two new problems on top of exercise 2:

**A reduction per row, not one for the whole array.** The natural mapping is one block
per row, which makes the reduction block-local — no cross-block communication at all,
so this is in one sense *easier* than exercise 2. The awkward case is `cols` much larger
than the block size (8 × 50257 is a real shape here: GPT-2's vocabulary), where each
thread must grid-stride within its row.

**Numerical stability, which is not optional.** `expf` overflows to `inf` above about
88.7 in FP32. Subtracting the row maximum first is mathematically a no-op — the
`exp(mᵢ)` factors cancel — and is the difference between working code and `NaN`. Read
`src/cpu_ref/softmax_cpu.cpp`, which does this and explains why.

This is also where FlashAttention starts. The online single-pass form of the same trick
— updating a running maximum and rescaling the running sum as you go — is the core idea
of that algorithm. You will implement it properly in 2027; recognising it here is the
point.

Note that `kernels.softmax_rows_survives_the_edge_cases` includes a row shifted by +300.
Its analytic error bound (1.8e-5) actually exceeds the test's `rtol`, and it passes
anyway because `exp(-300)` underflows to exactly zero on both sides. Do not read that
pass as evidence that the tolerance is loose enough for arbitrary inputs.

## Exercise 4 — `rmsnorm`

`out[i][j] = x[i][j] / sqrt(mean(x[i]²) + ε) · w[j]`, with `w` optionally null.

This one should feel easy, and if it does not, exercise 3 is not finished. It is the same
per-row-reduction shape — sum of squares instead of max-then-sum — so if you factored
your block reduction into a reusable `__device__` helper, most of this is already
written. If you did not, do it now rather than writing the same loop a third time.

Two details:

- **Use `rsqrtf`, not `1.0f / sqrtf(...)`.** It is a single hardware instruction, and it
  is also slightly more accurate here: differentiating `x^(-1/2)` shows the relative
  error is halved relative to the input's.
- **`weight` may be null**, meaning "no learned scale". The test passes a
  default-constructed `DeviceBuffer` (whose `get()` is `nullptr`) for that case, and
  `kernels.launchers_reject_null_pointers` asserts that a null `weight` is *accepted*
  while a null `in` or `out` is rejected. Do not add a blanket null check.

RMSNorm runs twice per transformer layer — 64 times per token in Llama-2-7B — so it is
worth getting right even though it is individually cheap.

## Exercise 5 — `matmul_naive`

`C[M×N] = A[M×K] · B[K×N]`, row-major, one thread per output element.

Deliberately the obvious implementation: each thread computes one `C[row][col]` by
looping over `k`. Write it, get it correct, and then work out from the code *why* it is
slow — `matmul_naive.cu` contains that arithmetic, and it is the whole motivation for
exercise 6.

The short version: each thread reads a full row of A and a full column of B from DRAM.
Every element of A is re-read N times and every element of B is re-read M times, so
actual traffic is about `2·M·N·K·4` bytes instead of the ideal `(MK + KN + MN)·4`. At
1024³ that is roughly 8 GB of traffic instead of 12 MB. The kernel is compute-bound in
theory and memory-bound in practice, and the gap between those two statements is the
lesson.

Note how the benchmark counts bytes: **ideal traffic**, each input read once and each
output written once. A naive kernel's re-reads therefore show up as a low achieved
bandwidth rather than a fictitious figure above hardware peak. That accounting choice is
what makes the naive and tiled rows directly comparable, and it is why tiling appears in
the table as the improvement it actually is.

Also note the two-dimensional indexing: `blockIdx`/`threadIdx` have `.x` and `.y`, and
which one maps to the row versus the column determines whether your reads coalesce.
Getting it backwards produces a kernel that is correct and several times slower. That is
worth measuring on purpose once.

## Exercise 6 — `matmul_tiled`

Same arithmetic, but each tile of A and B is staged in `__shared__` memory and reused by
every thread in the block.

**This is the deliverable of the ladder** and the headline result of objective 2. A
`TILE × TILE` tile loaded cooperatively is read from DRAM once and used `TILE` times, so
DRAM traffic falls by a factor of about `TILE`. With `TILE = 16` or `32`, expect a large
speedup over exercise 5.

Predict the factor from the tile width before you measure it. Being able to say "I
expected roughly 16x fewer bytes and measured 11x faster, the difference being launch
overhead and the partial edge tiles" is the actual skill this exercise is for.

The hard part is not the tiling, it is the edges. When M, N or K is not a multiple of
`TILE`, the tiles along the right and bottom edges are partial, and threads that would
read out of bounds must load `0.0f` instead — padding, not branching, so that
`__syncthreads()` is still reached by every thread in the block. This is why
`kernels.matmul_tiled_agrees_with_matmul_naive` tests 17×23×31: no dimension divides 16
or 32, so *every* edge tile is partial. Squares of 512 hide all of it. If your kernel
works at 512³ and fails at 17×23×31, the bug is in the edge handling, and that is the
common case, not the unlucky one.

**cuBLAS is the yardstick, not the competition.** `bench_kernels` measures
`cublasSgemm` alongside your two kernels. cuBLAS uses tensor cores, hand-tuned assembly
and shape-specific kernel selection; reaching 40–60% of it with a hand-written FP32
kernel is a genuinely good result and the honest way to report the work. It appears in
`bench/` only, never as an implementation — see
[ADR 0004](adr/0004-cublas-baseline-only.md).

When you report the matmul speedup, give both numbers: against `cpu::matmul` (how much
the GPU is worth) and against cuBLAS (how good your kernel is). Quoting only the first
is the kind of comparison this project should teach you to distrust — `cpu::matmul` is a
deliberately naive scalar triple loop, and a blocked multi-threaded AVX2 version would
be 50–100x faster than it.

## Exercise 7 — `gemv` (Autoregressive Decode Specialization)

During token generation, $M=1$. Applying a 2D tiled GEMM kernel like `matmul_tiled` to $1 \times K \times N$ leaves 31 out of 32 rows in every thread block idle, dropping achieved bandwidth to ~128.5 GB/s (25.5% peak).

**The idea:** Specialize the kernel for a 1D vector times a 2D matrix ($y = x \cdot B$):
- **1D Column Tiling:** Each block owns 64 columns of $B$. Grid dimension is `(N + 63) / 64`.
- **Warp Cooperation:** 256 threads per block (8 warps). Each warp processes 8 columns. The 32 threads in the warp divide the $K$ dimension, accumulating partial dot products.
- **Register Tree Reduction:** Within each warp, threads reduce across $K$ via `__shfl_down_sync` register shuffles across offsets 16, 8, 4, 2, 1.
- **Vectorized Loads:** Uses 64-bit `float2` loads to halve memory instruction count and maximize memory bus efficiency.

**The result:** Achieves **473.5 GB/s (94.0% of theoretical peak bandwidth)** on the RTX 4070 SUPER, beating cuBLAS by 13.7%.

## Exercise 8 — `rmsnorm_linear` (Pre-Sublayer Fusion)

In modern transformers, every attention and feed-forward block begins with `RMSNorm` followed immediately by a linear projection (`QKV` or `Gate/Up`).

**The idea:** Eliminate the intermediate DRAM roundtrip:
- Load the unnormalized input row into dynamic shared memory.
- Cooperatively compute the sum of squares across the block, compute the scale factor `rsqrtf(mean_sq + eps)`, and normalize in place in shared memory.
- Without ever writing the normalized activations to DRAM, execute the matrix multiplication accumulation loop by broadcasting normalized values directly from shared memory to registers.
- **Prefill ($M=512$):** Eliminates 16 MiB DRAM roundtrip (8 MiB write + 8 MiB read) per projection.
- **Decode ($M=1$):** Activations reside in the 48 MiB L2 cache; speedup is driven by eliminating 3–5 µs of kernel launch overhead.

## Exercise 9 — `residual_rmsnorm` (Post-Sublayer Fusion)

At the end of each sublayer, the sublayer output is added to the residual stream, and the result is normalized before passing to the next block (`x = x + sublayer; norm = rmsnorm(x)`).

**The idea:** Single-pass memory transaction:
- Threads read input `x` and `residual` once from DRAM.
- Compute the sum $s = x[c] + residual[c]$, write $s$ directly to the residual output buffer, and simultaneously accumulate $s^2$ into thread registers.
- Perform a block reduction to find the RMS scale, then write the normalized row to `norm_out`.
- Saves 8 MiB of DRAM read traffic at $M=512$, reducing traffic from 20 bytes/element to 16 bytes/element.

## Looking Forward: Module 4 & 5

With elementwise, reductions, 2D GEMM, decode GEMV, and sublayer fusion mastered, the engine transitions to end-to-end transformer components:

### Module 4: FlashAttention-2 (Oct – Nov 2026)
- **Tiled Attention:** Fuses $Q K^T$, online softmax scaling, and $P V$ accumulation into a single kernel.
- **Memory Advantage:** Never materializes the $S \times S$ attention matrix in DRAM, reducing memory footprint from $O(S^2)$ to $O(S)$.
- **Key Techniques:** Online softmax rescaling factors ($m_{new}, \ell_{new}$), double buffering in shared memory, and causal autoregressive masking.

### Module 5: Weight-Only Quantization (Nov – Dec 2026)
- **Memory Compression:** Packs FP16/FP32 weights into 4-bit (INT4) or 8-bit (INT8) integers, reducing memory footprint by $4\times$ to $8\times$.
- **Dequantization Kernels:** On-the-fly SIMD unpacking (`lop3.b32`, `prmt`) fused directly into the inner loop of `gemv`, enabling high token-per-second decoding speeds directly from memory-bandwidth constrained consumer GPUs.
